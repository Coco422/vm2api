# amd64 CLI 图片请求内存修复

此页记录候选源码与隔离验收，不代表生产已发布。生产实际版本以 `PRODUCTION_STATUS.md` 的现场核验为准。

原始 `cli-node` 的 SHA-256 为 `f6c3744dda01f756049360113607d2bd9a25911de0fdaf30fe9bb1a1918a6788`。上游 v1.4.238 沿用该文件。修复从这个公开制品解出摘要固定的 JS，在原生 Linux x86_64 使用摘要固定的 Bun 1.4.0 构建，不上传完整提取源码，不执行生产数据。

修复包含以下环节：

- 合并重复 JSON 规范化与 CCH 解析；使用 Bun 原生 xxHash64，保持原始种子与完整 64 位结果。
- CCH 的模型置空、fallbacks、credit token 和 max_tokens 投影改为单个 UTF-8 缓冲区就地压缩，保留原始顺序、逗号与数字处理语义，避免多份大 UTF-16 字符串。
- 出站头上报回调只捕获 job/slot 标识，避免 AsyncLocalStorage 经 watcher 保留整份请求。
- 启动作业时设置 running；取消会中止上游并等待清理。成功和失败路径等待响应头发送后再检查取消，避免已取消作业迟到的终结帧。

构建入口：

```sh
python3 deploy/build-cli-memory.py \
  --payload verified/share/wrap-cli/cli-node \
  --output staging/cli-node \
  --cache staging/tools
```

脚本验证原始 ELF、提取源码、投影模块、补丁后源码、工具归档、Bun 二进制及版本；同目录重复编译必须一致。发布前另在两个独立目录构建并比对，产物摘要由 `deploy/payload.json` 固定。`.manifest.json` 与 `.patch` 是构建证据，不含运行凭据。ARM 原生 overlay 独立保留原始输入和既有运行时，本次内存修复的验收范围为 amd64。

2026-11-27 的原生隔离验收使用 53 张有效 PNG、约 28.7MB JSON，包含中文和 emoji；PNG 填充用于匹配传输体量。该负载复现网关/CLI 的解析、序列化与传输，未验证模型侧图片解码或生产真实账号。原始请求完整图片数量未从脱敏预览确认，不能把此构造夹具称为完整生产请求副本。

- 投影逐字节对照：主验证 2,006 组，独立复核 33,600 组；覆盖字段排列、嵌套、转义、多字节、孤代理和数值边界。
- 完整原始/修复后 buildFetch：32 组正文类型、JSON/普通文本及 CCH 开关的正文、类型与头一致；额外 66 组原始 xxHash64 与原生实现完整结果一致。
- 最终 ELF：多槽、重复/过时/晚到取消、响应头前取消、流中取消及复用通过；响应头等待期间的成功/错误取消竞态另有 8 组原始反例及修复验证。
- 仅 kernel 与 CLI 位于独立 2GiB、无 swap 的 cgroup，mock/驱动在外：6 轮双并发、5 次取消、1 次复用通过，峰值 1,606,574,080 字节，空闲 31 秒后 612,790,272 字节。
- 延长至 30 轮双并发、每轮新 session，再取消与复用，共 66 条上游请求通过；峰值 1,874,231,296 字节，空闲 31 秒后 1,027,887,104 字节；两次均无 OOM、内存上限事件或服务重启。
- 同一夹具、内核和独立 2GiB 限制，换回原始 CLI 的对照实际触发 1 次 OOM kill、258 次上限事件，约 38 秒失败。
- 另在同来源补丁 JS 加仅实验室使用的 WeakRef/heap 探针：20 个新 session 完成后，历轮对象没有累积，普通采样仅剩最后一个尚未 GC 的请求；一次诊断 GC 后存活请求为 0、JS heap 约 27.2MB，5 秒后 RSS 约 232.4MB。探针、手动 GC 均不包含在正式 ELF 中。

上述容量证据覆盖两路大请求，不保证任意数量的满上下文图片请求都能在 2GiB 内运行。空闲 RSS 包含分配器保留页，不能单凭 RSS 判断会话对象泄漏；对象可达性、正常 GC 和长期峰值应分开核验。没有调整生产并发、内存保护阈值或代理。

逐槽发布使用管理员原有 `POST /api/panel/wrap-cli/sync`，明确传入一个现存 VM 的 `ids`、`mode:"keep"` 和 `restart:true`。该入口持有当前主控的 VM 生命周期锁、维护标记和看门狗 hold，等待实际在途与队列自然排空；检查失败时不发布。省略单槽范围仍沿用原批量入口，不能将其视作本次保留容器的更新路径。`restart:false` 只检查，不安装。

受支持的远端 Docker 布局使用只读 `slot-bin` 目录绑定、独立固定 IP bridge 和同槽宿主出口辅助容器。本机布局使用 `cli-home` 目录绑定、已知内核入口、单 endpoint 的专属 bridge 和已归属的宿主出口辅助容器。本机仅原子更新 CLI 和内核 ELF，要求现有包装器与 glibc 已兼容，不重建容器或改内核配置。具体发布前仍须验证实际布局、制品摘要、目录安全与运行资源；未知布局明确拒绝。

租户暂停属于调度状态，不能据面板 `paused` 判定 Docker 已物理暂停；带有明确租户暂停标记且 Docker 实际运行的槽可以保持暂停完成升级。物理暂停和不支持的停机布局需另行核验，不自动启动。运行槽发布后须独立核对同一容器 ID、RAM/swap、配置摘要、暂停原因、实际出口以及 `/proc` 中实际映射的 CLI/内核字节，磁盘文件或主控镜像更新不代表进程已经更新。部分发布、重启或后续拓扑校验失败时保留故障禁调度，由现场核验后恢复，不能直接清除租户暂停。
