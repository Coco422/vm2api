## 双机容量关系示例（旧批次席位按原配置）

管理员先确认两台VM都属于同一用户，平台、模型权限、账号、独立出口和内核均可用，再显式设置Key允许范围。示例交付目标为两个VM各12请求并发、用户合计24：

| 层次 | 需要核对的有效值 | 说明 |
| --- | --- | --- |
| 用户 | `users.concurrency=24` | 全部Key的在途请求合计上限，包括已准入、尚在等VM的请求 |
| 单把Key | `max_concurrency=24` | 只改Key不能突破用户总上限；额度/RPM/有效期也需分别核对 |
| Key资源范围 | `group_type=anthropic`，`allowed_vms=[本人VM_A, 本人VM_B]` | 不能将`all`当作静态双机名单；调度还会重新验证VM归属 |
| VM_A、VM_B | 每台`max_concurrency=12` | 现有`concurrency_override=true`时，全局分档调整不会改变单机值 |
| 会话席位 | 按实际独立活跃对话数配置，并核对配额余量 | 席位数不是请求并发。20个内核预开槽也不代表账号可承诺20个并发 |
| 调度 | 同档优先级下`balanced` | 设备、会话和父子会话亲和优先；不能承诺每个请求严格五五分配 |

这些值应由管理员工具写入后回读确认。**当前原生用户面板没有用户总并发入口**，不能只在Key对话框选24就宣称交付了24总并发；本次没有新增用户API或修改数据库结构。Key面板已补12、24选项，管理员设置用户总并发仍需使用已授权的运维流程和现有用户仓库接口。

客户端每个对话使用独立且稳定的session ID；同一活跃session保持在一台VM，不会因新增第二台而线性加速。验证24总并发应使用多个独立会话及真实可用的账号资源；不能用生产真实模型盲测。用户/Key上限只是准入上限，不是吞吐SLA。

## 两台 VM 各一把 Key

每把Key明确绑定各自VM，例如每把12、每VM12。两把Key仍合计受同一个用户总上限约束：用户是12时两把合计12，用户是24时才可能合计24。单机Key失败不会自动借用另一把Key的VM。客户端或业务方自行选择Key，也不能将不同账号的服务端续写状态视为可任意迁移。

2026-11-04只读交接证据中的vm12用户正是两把Key分别绑定原vm-12与补偿VM的配置，用户总并发仍12。未调整这些线上绑定或上限。

## 自助 Key 的兼容边界

新建自助Key继承管理员明确设置的正数用户并发；用户未设置正数上限时使用新Key全局默认值，缺省12。所有Key依旧共用既有用户累计门禁，不新增租户预算。既有Key不会随用户上限改变而自动改值，需要管理员单独核对。底层Key字段仍有既有128上限，不能把任意用户授权值直接视为有效Key上限。

单平台自助Key保存创建时的本人VM快照，之后新增VM不会自动追加；重新分配给别人的VM即便仍在名单中，也被实时归属检查拒绝。混合Claude/GPT自助Key保留既有`group_type=all`语义：在本人资源范围内动态选取，不是静态快照。需要固定名单时由管理员分别发Anthropic/OpenAI平台Key，不扩大`all`的公共契约，也不让用户自己改资源范围。

## 席位排队的判断顺序

1. 先区分Key/用户准入429、调度队列等待、内核slot_busy、上游额度及内核不可用。Key/用户准入在选VM前发生，不能把所有在途数当成已在推理的数量。
2. 正常对话最后一个请求结束且无排队后续时释放席位，sticky TTL只保留VM记忆。`seat_grace_ms=30000`是兼容字段，不表示普通请求结束继续占位30秒。
3. 补偿VM的当前4席位会限制同时活跃的独立会话，即使请求并发为12。历史排队样本不能证明历史上始终是4席位；先确认这是否为刻意交付限制、当时账号余量、会话数与内核健康，再决定是否调整。
4. 新会话亲和VM席位满时，默认先等45秒，再进入全局队列等最多30秒；已有席位的同session并发等待可能直接超时。实际还受总重试期限约束，不保证总能换机。
5. 关闭`block_on_5h/7d`不等于取消所有准入保护。`seat_budget_reserve_pct=0.02`仍要求新席位覆盖已有席位的保留量；例如可用余量确为0.05时，预算公式最多容纳2个席位，第三个需0.06。不要用盲目扩大席位或关闭保护处理临界耗尽。
6. 下线、额度硬门禁、熔断、失效时只在同一用户且同Key合法范围内迁移。v1.4.038的#872修复迁移后的出站session持久化；临时借用不应覆盖原绑定，迟到结果不能覆盖新的绑定。
